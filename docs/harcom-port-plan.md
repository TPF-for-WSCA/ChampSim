# ChampSim HARCOM port plan

Use ChampSim's trace reader, timing model, and module interfaces to drive physical models of the simulated hardware. Port on-chip structures to HARCOM in stages and use a DRAM command model for off-chip memory. The first whole-system target is the simulated processor, its on-chip memory hierarchy and interconnect, and the attached DRAM channels. Platform devices such as storage, power delivery, and peripherals sit outside that boundary.

HARCOM estimates dynamic energy, circuit delay, and hardware cost for operations expressed with its hardware types. Its leakage estimate uses modeled device counts and a simplified leakage model. The reviewed CBP-NG revision uses a nominal 0.75 V and activity assumptions for logic. Treat that revision as a reference technology point and record it with every result. [CBP-NG documentation](https://github.com/AmpereComputing/cbp-ng) · [Pinned HARCOM source](https://github.com/AmpereComputing/cbp-ng/blob/5ceea8358ddbab94e5621e2536530b860cc1e5b7/harcom.hpp)

## Integration design

- **Timing and state.** Keep ChampSim authoritative for instruction flow, contention, speculation, and event time. Use direct HARCOM implementations for stateful structures that can be ported with functional parity. For structures whose hardware payload or activity is absent from the trace, use a parameterized circuit characterized with HARCOM or an explicitly sourced component model, driven by the corresponding ChampSim events. Use one energy model per physical structure. Keep modeled circuit delays available for timing checks before any later experiment connects them to ChampSim scheduling.
- **Hardware descriptions.** Resolve width, depth, banking, ports, and data paths from the selected configuration and an explicit hardware description. Avoid deriving them from the size of simulator structs or C++ containers. Instantiate fixed-width HARCOM models for supported geometries and emit a coverage entry for unsupported ones. Treat port conflicts as a model discrepancy requiring a justified banking, replication, or scheduling choice.
- **HARCOM lifetime.** Pin the dependency and isolate its C++20 interface from the existing build. At the reviewed revision, HARCOM shares a global panel, requires RAM creation before floorplanning, and limits accesses per modeling cycle. Construct hardware models before simulation starts. For the first implementation, use one model lifetime per process and characterize large components or clock domains independently where appropriate. Measure the floorplan and runtime cost before choosing any shared on-chip floorplan representation. HARCOM modeling cycles and ChampSim elapsed time serve different purposes. [Pinned HARCOM source](https://github.com/AmpereComputing/cbp-ng/blob/5ceea8358ddbab94e5621e2536530b860cc1e5b7/harcom.hpp)
- **Accounting.** Start with opt-in estimates and preserve existing results when estimation is disabled. Charge operations when their modeled hardware action occurs, including accesses caused by speculative work later squashed, and keep state through warmup. Take cumulative snapshots at phase boundaries in [the simulator loop](../src/champsim.cc). Use a single elapsed window from the end of warmup through completion of the measured phase for the whole-system result. If reporting per-core ROI windows as well, retain their own duration and keep them out of the whole-system sum.

Begin with gshare and a conventional cache topology for reproducible checks, then qualify the repository configuration's TAGE-SC-L, FDIP, Berti, and Pythia as part of extending coverage. Choose a concrete DRAM device and check its organization and clock against the configured geometry before reporting a DRAM estimate.

## Trace coverage and calibration

The [instruction trace formats](../inc/trace_instruction.h) provide PCs, register identifiers, branch flags, and memory addresses. They omit opcode mix, register values, and cache-line payloads. ChampSim can derive access counts, address activity, and queue behavior from these traces. Execution-unit mix, data toggling, and associated energy need explicit assumptions or a richer trace. Define a documented default and sweep plausible activity and instruction-mix inputs. Use richer traces when validating claims that depend on operand-level switching.

Validate SRAM and structure costs against a second model such as CACTI and compare core estimates with a suitably configured McPAT model or an RTL reference. Differences in voltage, temperature, ports, and clock gating affect absolute numbers. Use the reference technology for relative comparisons first and record calibration evidence before drawing absolute power conclusions for a specific processor. Characterize leakage from the modeled circuit inventory and operating assumptions. Peak modeled activity and circuit size are different quantities. [McPAT and CACTI-P documentation](https://github.com/HewlettPackard/mcpat)

## Output and completion criteria

- Report component instance, model revision, clock domain, measurement interval, coverage status, and model assumptions alongside energy. Include dynamic and leakage energy where available. Preserve DRAM command, background, and interface terms so users can reconcile them with the total.
- Use joules and watts in the aggregate interface. For each component, integrate leakage power over simulated residency time and divide total energy by elapsed simulated seconds for average power. For example, 10 nJ over 100 µs gives 0.1 mW. Leave average power unset for a zero-duration window. Publish energy per retired instruction using retirement counts from the same window.
- Include a modeled subtotal and explicit coverage gaps for partial configurations. Publish a whole-system total once all required blocks in the stated boundary have estimates and the component sum reconciles. Require trace parity between estimation enabled and disabled for the reference configuration, plus deterministic reruns, a zero-warmup case, and a multicore case with unequal ROI lengths.

The first implementation change is milestone 1. Its acceptance checks establish the phase accounting and simulation parity that the remaining component ports will rely on.
